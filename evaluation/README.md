# DNS and ICMP detector evaluation

The unit of evaluation is **one transfer or diagnostic sequence**, not one
packet. The default run evaluates 100 benign and 100 malicious sessions for
each protocol:

```bash
uv run python -m evaluation.run_covert_eval
```

`dns/sessions.csv` and `icmp/sessions.csv` are the primary results. A session
is grouped by source, destination, and DNS apex where applicable, with a new
session after more than 60 seconds of inactivity. A session is detected if any
of its packets alerts. `results.csv` in each folder gives every packet's full
payload, detector rule IDs, and complete detector messages. Both files have a
`session_id` for joining. The session CSV shows packet IDs, a payload preview,
the first alert message, and all rules fired during the sequence.

The `outcome` field in `results.csv` describes whether that **packet** alerted.
The `outcome` in `sessions.csv` is the TP/FP/TN/FN classification of the
**whole sequence**. Use the latter to calculate detection and false-positive
rates. `--benign-count` and `--malicious-count` both count sessions. The
bundled DNS tool capture and manifest contain 100 malicious sessions.

## Current sample

| Protocol | Benign sessions | Malicious sessions | Benign packets | Malicious packets |
| --- | ---: | ---: | ---: | ---: |
| DNS | 100 | 100 | 260 | 140 |
| ICMP | 100 | 100 | 300 | 180 |

All file contents, text strings, and host addresses used for generated tool
runs are dummy test data. Session inputs are deterministic and distinct. The
malicious label records their use in an exfiltration tool workflow, not the
sensitivity of the dummy bytes.

## Malicious sources

**DNS:** The 100 sessions were generated by calling the actual `Client.dns_ask`
packet builder from [zrckr/dns-tunnel](https://github.com/zrckr/dns-tunnel)
at commit `93cfb4a2ff3c53c9e32142ea518cbbcaf7dacf7d`. Fifty runs use its
text-transfer mode and fifty use its file-transfer mode. Each run has a unique
input, source IP, and run-specific domain. The exact input digest, packet
count, mode, and query type for each run are in
[`dns/tool_sessions_manifest.csv`](dns/tool_sessions_manifest.csv). The
generated queries are bundled in [`dns/tool_sessions.pcap`](dns/tool_sessions.pcap)
(SHA-256 `f326de01689bf8289ee7ea2e149564ec0699195a0592b66aa75e42f8b9cc6a43`).
The tool's source is not copied into this repository; the generator imports
it from a separate checkout and never calls its network send function.

To regenerate those 100 DNS sessions with the same external source and
dependency versions:

```bash
git clone https://github.com/zrckr/dns-tunnel.git /tmp/dlp_dns_tunnel
git -C /tmp/dlp_dns_tunnel checkout 93cfb4a2ff3c53c9e32142ea518cbbcaf7dacf7d
uv pip install --target /tmp/dlp_dns_tool_deps dnslib==0.9.26 bitstring==5.0.0 pycryptodome==4.0.0
PYTHONPATH=/tmp/dlp_dns_tool_deps python -m evaluation.dns.generate_tool_sessions --tool-dir /tmp/dlp_dns_tunnel
uv run python -m evaluation.run_covert_eval
```

**ICMP:** The 100 sessions use [Smendowski et al.'s `icmp.py`](https://github.com/Smendowski/hidden-communication-using-covert-channels/blob/main/icmp.py),
copied to `icmp/external_icmp.py` with its MIT license in
`icmp/EXTERNAL_LICENSE` (source SHA-256
`6a1afd034959323e24164f1cb717a8746854776d1da9f28cdddf31420895eb90`).
The harness calls its file fragmentation, base64 encoding, payload framing,
and packet constructor 100 times with distinct seeded dummy files and source
IPs. It does not call the tool's send function.

The earlier [iodine capture](https://github.com/Korving-F/dns-tunnel-dataset)
is kept as `dns/iodine_sample.pcap` for reference. It contains one transfer
sequence and is **excluded** from the current 100-session results.

## Connection to related research

The selected generators produce the two exfiltration mechanisms this project
detects: data carried in DNS queries and data carried in ICMP Echo payloads.
They also expose packet construction functions, which let the harness create
100 distinct transfers per protocol without sending traffic. Their source
code and exact input generation make this experiment reproducible.

The connection to peer-reviewed work is **the mechanism, not these exact
implementations**. [Chen et al. (2021)](https://doi.org/10.1016/j.cose.2020.102095)
generated DNS covert-channel traffic with eight tools, including iodine,
dnscat2, and dns2tcp. The current 100-session DNS generator, `zrckr/dns-tunnel`,
is not among those tools. The bundled iodine capture is a separate reference
sample and does not contribute to the current metrics.

[Tu et al. (2022)](https://doi.org/10.32604/cmc.2022.022540) generated ICMP
covert-tunnel traffic with tools including icmptunnel, ptunnel, and icmpsh.
Our ICMP generator is [Smendowski et al.'s documented project code](https://github.com/Smendowski/hidden-communication-using-covert-channels),
which places base64 file chunks and sequence information in ICMP Echo payloads;
it is not one of the tools evaluated by Tu et al. We found no peer-reviewed
paper tied directly to either selected generator. The reports therefore cite
the papers as support for the threat models, not as validation of these tools
or of our measured detector performance.

## Benign sources and limits

Benign sessions are deterministic local fixtures: ordinary DNS lookups,
service discovery, cache-busting names, and Linux/Windows/default or custom
ICMP Echo diagnostics. They are not production traffic. The benign mix
intentionally includes patterns that can challenge the detector, so its
false-positive rate is specific to this sample.

Replay calls the production packet parsers and detection functions, with
fresh detector state for each label group. It does not test live sniffing,
routing, dropped packets, or gateway blocking. The Docker lab had no running
containers when the evaluation was performed.

The existing targeted DNS/ICMP test run had 47 passes and one failure:
`test_whitelisted_linux_ping_prefix_is_still_inspected`. That failure shows
an encoded secret in a Linux-shaped ICMP Echo prefix can evade the current
detector; it is distinct from the external tool's default large-packet
transfers and is documented in the ICMP report.
