# Detector evaluation

The unit of evaluation is **one transfer, diagnostic sequence, or HTTP
exchange**, not one packet or request. Two scripts drive the evaluation:

```bash
uv run python -m evaluation.run_covert_eval   # DNS + ICMP (100+100 sessions each)
uv run python -m evaluation.run_l7_eval       # L7 Web (14+10 sessions)
```

`dns/sessions.csv`, `icmp/sessions.csv`, and `l7_web/sessions.csv` are the
primary results. For DNS and ICMP a session is grouped by source, destination,
and DNS apex where applicable, with a new session after more than 60 seconds of
inactivity. For L7 Web a session is one HTTP scenario (one or more requests
under a single `session_id`). A session is detected if any of its packets or
requests alerts. `results.csv` in each folder gives every packet's or request's
full payload, detector rule IDs, and complete detector messages. Both files
have a `session_id` for joining.

The `outcome` field in `results.csv` describes whether that **packet or
request** alerted. The `outcome` in `sessions.csv` is the TP/FP/TN/FN
classification of the **whole session**. Use the latter to calculate detection
and false-positive rates. For the covert-channel run, `--benign-count` and
`--malicious-count` both count sessions.

All file contents, text strings, and host addresses used for generated tool
runs are dummy test data. Session inputs are deterministic and distinct. The
malicious label records their use in an exfiltration tool workflow, not the
sensitivity of the dummy bytes.

Replay calls the production packet parsers and detection functions, with
fresh detector state for each label group. It does not test live sniffing,
routing, dropped packets, or gateway blocking (the one exception is L7
end-to-end latency, which is sampled separately via `curl` through the full
Docker + mitmproxy stack and reported in the main `README.md` section 4.1).
The Docker lab had no running containers when the covert-channel evaluation
was performed.

Benign sessions, for every protocol, are deterministic local fixtures, not
production traffic — each protocol's section below describes how its own
benign mix is built, and why. Each protocol's false-positive rate is specific
to its own sample.

## ICMP evaluation

### Benign sessions and packets

Benign ICMP sessions are generated by `icmp_benign_packets`
(`evaluation/run_covert_eval.py`), seeded for reproducibility. Each of the 100
sessions is independently assigned one of three kinds by weighted random
choice: **40% `linux_default_ping`** (a real 56-byte Linux Echo payload — a
16-byte `timeval` set to the actual current time, split into `tv_sec`/`tv_usec`,
followed by the fixed 40-byte counting pattern a real Linux ping sends), **30%
`windows_default_ping`** (the fixed 32-byte Windows `a`-`w` payload), and
**30% `custom_ping`** (a random byte string at one of six non-default sizes —
32, 48, 56, 64, 100, or 120 bytes — standing in for "a ping the detector
doesn't recognize," e.g. a different OS or a custom `-s`/`-l` size). Each
session sends 1–5 packets (uniform random) from a unique synthetic source IP.

The `linux_default_ping` timestamp must be real wall-clock time because the
detector's own validation (`is_valid_linux_timestamp`, added by issue #11's
fix) checks the payload's `tv_sec` against `time.time()` at detection time —
see the evaluation-finding writeup below for a case where this fixture got
that wrong.

### Malicious sources

The 100 sessions come from **two** real tools because the detector inspects
ICMP payloads three ways — structure (size / pattern), rate (per-source
frequency), and content (regex, Luhn, Shannon entropy). One tool and one input
shape would leave most of that surface unmeasured, so each tool is driven across
several input profiles, all sampled with a fixed seed (**stratified random**:
each run is assigned a profile from a balanced, shuffled pool, and sizes, packet
counts, send cadence, and dummy tokens are drawn randomly per run). Every packet
is still produced by the tool's own builder — randomness only chooses the input
bytes and timing, never a hand-crafted packet.

*icmptunnel — structure, rate, and cleartext-content (50 sessions):*
[DhavalKapil/icmptunnel](https://github.com/DhavalKapil/icmptunnel) at commit
`267a9ec7af03bf05f467d94550f15a969bfb8611`, named (without a repository or
version) among the traffic sources in the
[ICMPTend study](https://doi.org/10.32604/cmc.2022.022540). The generator frames
dummy-file bytes inside IPv4/UDP datagrams and calls the tool's original C
`send_icmp_packet`; an offline adapter intercepts `sendto` and writes the bytes
to a PCAP, opening no sockets. Four profiles: **oversized** (random large files →
`icmp_oversized_payload`), **tiny** (random ≤64 B payloads → `icmp_non_standard_size`),
**burst** (a random >4-chunk transfer sent sub-second → `icmp_high_frequency`),
and **secret** (a Luhn-valid dummy card plus a randomly chosen dummy API token,
left readable by the raw framing → `icmp_sensitive_data_luhn_cc` and token
regexes). Capture and per-run profile/hashes: `icmp/icmptunnel_sessions.pcap` and
`icmp/icmptunnel_manifest.csv` (PCAP SHA-256
`cc1ab06a4ff270ac78ae982dcd9b7cbd44886d23b6794b71f73719612a55ea47`).

*Smendowski — base64 content / entropy (50 sessions):*
[Smendowski et al.'s covert-channel tool](https://github.com/Smendowski/hidden-communication-using-covert-channels),
vendored as `icmp/external_icmp.py` (SHA-256
`6a1afd034959323e24164f1cb717a8746854776d1da9f28cdddf31420895eb90`, MIT license
in `icmp/EXTERNAL_LICENSE`). It base64-encodes each file chunk before framing,
placing a high-entropy ASCII token in the Echo payload. The generator calls its
`create_icmp_payload` builder on random-size dummy files; the returned scapy
packets are written straight to a PCAP, with no send. Capture and per-run input
hashes: `icmp/smendowski_sessions.pcap` and `icmp/smendowski_manifest.csv` (PCAP
SHA-256 `48b09ef168ba04fadf79b5fab7e2b380c33a0dee963a20c708023c400cad6ab6`).
These transfers trip `icmp_sensitive_data_high_entropy`, the signal raw binary
never forms (the content scan's UTF-8 decode drops its non-ASCII bytes).
While the tool does not stem from a paper of its own, it has been used in other
academic work on covert channels, e.g. [Fokin and Yevdokymenko (2025), *An
Overview of Covert Channels in Software Defined Networks*](https://doi.org/10.1109/IDAACS68557.2025.11322109)
(IEEE IDAACS).

Both exercise the tools' packet framing, not a live end-to-end tunnel. The
icmptunnel source is loaded from a separate checkout; the Smendowski tool is
vendored because it is a single documented file.

To regenerate both ICMP captures:

```bash
git clone https://github.com/DhavalKapil/icmptunnel.git /tmp/dlp_icmptunnel
git -C /tmp/dlp_icmptunnel checkout 267a9ec7af03bf05f467d94550f15a969bfb8611
uv run python -m evaluation.icmp.generate_icmptunnel_sessions --tool-dir /tmp/dlp_icmptunnel
uv run python -m evaluation.icmp.generate_smendowski_sessions
uv run python -m evaluation.run_covert_eval
```

### Connection to related research

The selected generators produce ICMP Echo payloads carrying hidden data,
exposing packet construction functions that let the harness create 50
distinct transfers per tool without sending traffic.

[Tu et al. (2022)](https://doi.org/10.32604/cmc.2022.022540) generated ICMP
covert-tunnel traffic with tools including icmptunnel, ptunnel, and icmpsh. We
use the public [DhavalKapil/icmptunnel](https://github.com/DhavalKapil/icmptunnel)
for the raw-binary path and
[Smendowski et al.'s tool](https://github.com/Smendowski/hidden-communication-using-covert-channels)
for the base64 path. The paper does not publish the exact source repository,
version, or capture used there, so this is a method-level connection, not a
replication of its dataset or detector. ICMPTend is the paper's SVM detector,
not the tool used to generate these packets. The base64-over-ICMP technique is
independently documented by purpose-built data-exfiltration test tools such as
[PyExfil](https://github.com/ytisf/PyExfil), whose ICMP module base64-encodes
files specifically to test DLP systems, and [SensePost's DET](https://github.com/sensepost/DET);
these are cited as evidence that the technique is real and tooled, but are not
run here (PyExfil's ICMP module is Python 2 / impacket and not offline-runnable
unmodified). The paper does not validate our measured detector performance.

## DNS evaluation

### Benign sessions and packets

Benign DNS sessions are generated by `dns_benign_packets`
(`evaluation/run_covert_eval.py`). Each of the 100 sessions gets a unique
synthetic source IP and a per-session pseudo-zone (`zoneNNNN.example`), and is
assigned one of four scenarios by `session_index % 10`: **cache-busting**
(20%, one query for a random-looking asset hostname — a single long,
high-entropy-looking label that can challenge the length/entropy rules
without being a real secret), **ordinary-lookup bursts** (10%, ten queries in
one session, to stress the volume rule with legitimate traffic), **service
discovery** (20%, two `_sip._tcp.<service>`-style SRV-like lookups), and
**ordinary lookups** (50%, two plain `service-N.zone.example` queries). Query
types are mostly `A` records, with a `TXT` record every seventh query. All
inputs are deterministic per session index, so the sample is reproducible
across runs.

### Malicious sources

The 100 malicious sessions come from **two** real tools. Ninety-nine
are generated by calling the actual `Client.dns_ask` packet builder from
[zrckr/dns-tunnel](https://github.com/zrckr/dns-tunnel) at commit
`93cfb4a2ff3c53c9e32142ea518cbbcaf7dacf7d` (50 text-transfer runs and 49
file-transfer runs); the remaining session is one recorded transfer from a
second, independent tool, **iodine** (`dns/iodine_sample.pcap`, scenario
`iodine_reference`). Each zrckr run has a unique input, source IP, and
run-specific domain. The exact input digest, packet count, mode, and query type
for each zrckr run are in
[`dns/tool_sessions_manifest.csv`](dns/tool_sessions_manifest.csv). The
generated queries are bundled in [`dns/tool_sessions.pcap`](dns/tool_sessions.pcap)
(SHA-256 `f326de01689bf8289ee7ea2e149564ec0699195a0592b66aa75e42f8b9cc6a43`).
The tool's source is not copied into this repository; the generator imports
it from a separate checkout and never calls its network send function. The
iodine session carries 100 recorded query packets, which is why the DNS
malicious packet total is higher than the session count.

The [iodine capture](https://github.com/Korving-F/dns-tunnel-dataset) in
`dns/iodine_sample.pcap` is one recorded transfer sequence from the iodine
DNS-tunnel tool. It is **included as one of the 100 malicious DNS sessions**
(scenario `iodine_reference`) so a second, independent tool is represented; the
detector flags it (`DNS_LONG_QNAME`, `DNS_HIGH_ENTROPY`, `DNS_TUNNEL_VOLUME`).

**Why not dnscat2:** dnscat2 appears in the related-research mapping below
(Chen et al. used it as one of eight tools) but was not added as a third
generator here. Unlike zrckr/dns-tunnel and iodine, dnscat2 has no static
"build one packet" function to call offline and no public pcap dataset of its
traffic that we could find , hence it was not included for our evaluation.

To regenerate those 100 DNS sessions with the same external source and
dependency versions:

```bash
git clone https://github.com/zrckr/dns-tunnel.git /tmp/dlp_dns_tunnel
git -C /tmp/dlp_dns_tunnel checkout 93cfb4a2ff3c53c9e32142ea518cbbcaf7dacf7d
uv pip install --target /tmp/dlp_dns_tool_deps dnslib==0.9.26 bitstring==5.0.0 pycryptodome==4.0.0
PYTHONPATH=/tmp/dlp_dns_tool_deps python -m evaluation.dns.generate_tool_sessions --tool-dir /tmp/dlp_dns_tunnel
uv run python -m evaluation.run_covert_eval
```

All 30 false positives are `cache_busting` (20, tripping `DNS_LONG_QNAME` on

### Connection to related research

The selected generators produce data carried in DNS queries, exposing packet
construction functions that let the harness create 100 distinct transfers
without sending traffic. The connection to peer-reviewed work is **the
mechanism, not these exact implementations**.
[Chen et al. (2021)](https://doi.org/10.1016/j.cose.2020.102095)
generated DNS covert-channel traffic with eight tools, including iodine,
dnscat2, and dns2tcp. Our main generator, `zrckr/dns-tunnel`, is not among those
tools; **iodine is** — the single `iodine_reference` session is the one point
of direct overlap with a tool used in that study, while the other 99 sessions
exercise the same mechanism with a different generator. The paper does not
validate our measured detector performance.

## L7 Web (HTTP) evaluation

### Malicious sources

No external attack tool with a published packet builder
exists for L7 DLP in the way `zrckr/dns-tunnel` and `icmptunnel` exist for the
covert channels; the standard literature evaluates L7 DLP against hand-crafted
PCI / API-key samples or curated HAR dumps. The 14 malicious scenarios are
therefore defined inline in `evaluation/run_l7_eval.py` and cover three
categories: credit cards (6 scenarios: Visa plain, dashed, URL-encoded dashes,
nested in JSON; Mastercard; Amex), API tokens (5 scenarios: AWS access key,
GitHub token, OpenAI user key, JWT, Stripe test key), and the three
WS-D.1 evasion vectors (invisible-unicode spacing, gzip compression, and
multi-request chunking, see `docs/l7-evasion-hardening.md`). The evasion
cases are the ones the detector is expected to miss on the baseline build;
their patches are opt-in or architectural and tracked in that document.

The scanner is called directly through the production `decode_body` +
`scan_all` entry points (the exact same code path the mitmproxy addon
executes on live traffic). No HTTP requests are sent by the script.

### Benign sessions and packets

The L7 Web sample is smaller and hand-crafted on purpose. The L7 pipeline is
deterministic per request (same input -> same findings), so additional samples
of the same attack technique add no statistical insight. Breadth of attack
vectors is what matters, and the 14 malicious scenarios cover six credit-card
variants, five API-token classes, and three of Diogo's evasion vectors.

Benign traffic patterns for L7 (form submissions, UUIDs, SHA-256 hashes, UPS
tracking numbers, random 16-digit order IDs, IPv4 pairs, lorem ipsum, JSON API
responses) intentionally include patterns that can challenge the detector —
the long hex and digit strings and the random 16-digit ID are chosen to
stress the Luhn pre-filter and the entropy threshold without being real
secrets.

To regenerate the L7 results:

```bash
uv run python -m evaluation.run_l7_eval
```

## Peer review and the detection / false-positive tradeoff

As part of the team's mutual manual validation of each other's detectors, Sofia
reviewed Antoine's ICMP detection (`detection/covert_channel/icmp_detector.py`,
notes in `docs/icmp-evasion-hardening.md`) and found that a packet classified as
a benign Linux ping still carried about 20 attacker-controlled, uninspected
bytes -- the unvalidated 16-byte timeval prefix plus the ICMP id/seq header
fields -- enough for a silent exfiltration channel that tripped none of the
three checks. This was filed as
[issue #11](https://github.com/AntoineQ1/DLPDetection/issues/11)
and pinned as the regression test
`test_whitelisted_linux_ping_prefix_is_still_inspected`.

Antoine's fix (commit `ea2ac4c`, *"validate Linux timeval and inspect ICMP
header fields"*) validates the 16-byte prefix and passes the id/seq bytes
through the L7 content scanner. The regression test passes and the ICMP suite
is green, and no malicious detection was lost (still 100%).

**This fix's false-positive cost was initially measured, and reported, wrong.**
An earlier version of this evaluation showed the fix roughly doubling the ICMP
benign false-positive rate, from 27% to 65% of sessions, attributed to default
Linux pings now tripping `icmp_abnormal_pattern`. That number turned out to be
mostly a bug in this harness's own `linux_default_ping` fixture: it set the
payload's `tv_sec` field to the tiny session index (`1`, `2`, `3`, ...) instead
of a real timestamp, which is exactly what Antoine's fix (correctly) rejects as
stale. A real Linux ping's timestamp is always "now," so the fix was never
going to reject genuine traffic — see `docs/icmp-evasion-hardening.md` for the
full writeup. Once the fixture was corrected to use a real `time.time()`
timestamp, the Linux-whitelist hardening's actual false-positive cost is
**~zero** (0/38 `linux_default_ping` sessions, down from 38/38), and the true
ICMP benign false-positive rate is **27%**, not 65% — entirely driven by the
`custom_ping` scenario's random-byte payloads at non-default sizes, which is a
separate, pre-existing ambiguity (see `docs/icmp-evasion-hardening.md`'s notes
on investigating and ultimately not pursuing a fix for it) and not a cost of
this hardening.

So the central tradeoff this evaluation originally surfaced — closing the
Linux-prefix steganography channel at the cost of benign precision — does not
actually hold up: the channel is closed, malicious detection stayed at 100%,
and real Linux diagnostic traffic is unaffected.
